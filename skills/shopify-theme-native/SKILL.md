# Shopify 主题原生融合开发

核心要求：定制能力可复用，定制模块与当前主题的架构、视觉和交互自然融合。先理解目标主题，再扩展它。Everwallpaper 和 Inyouths 是经验来源，不是所有新站都必须套用的源码模板。

## 所有操作的工具选择原则

用户偏好适用于本 Skill 内的所有操作，不限于店铺后台修改：只要存在方便、可行的非浏览器方式，就优先使用专用工具、API、CLI、本地脚本或直接文件操作，不操控浏览器完成同一任务。读取与检索、代码编辑、配置、上传下载、检查验证均遵循这一原则。技术资料优先通过文档工具或直接检索读取，无需打开浏览器界面。

只有非浏览器方式无法满足实际需求，或必要的交互登录、视觉与交互验证确实需要浏览器时，才使用浏览器，并将操作限定在必要范围。不要因为习惯或方便编写点击流程而跳过已有的非浏览器方式。

## 店铺连接与操作顺序

用户指定 Admin API 优先：已有可用的店铺 Admin API 凭据或连接，且支持本次操作时，优先通过 API 读取主题、数据和执行已授权的修改。先确认目标店铺、主题及相关权限，不重复索要已提供且仍有效的连接信息。

没有可用的 Admin API 凭据、连接或相关权限时，使用 Shopify CLI 登录连接目标店铺，完成其支持的主题拉取、开发预览与上传。需要用户参与登录时说明具体步骤。CLI 仍需有效登录和店铺权限，不能绕过访问限制。

尽量不操控浏览器。凡 API 或 CLI 能完成的读取、代码修改、配置更新、上传等操作，直接通过 API 或 CLI 完成，不进入浏览器后台编辑，也不为了方便改走浏览器。必要的交互式登录与开发后的视觉预览不等于后台修改；仅在任务确有需要时使用。

实施时核对当前官方 API 或 CLI 文档与实际可用能力；不把旧 API 版本、端点或命令写死为跨项目规范。只有确认 API 和 CLI 均无法完成的必要操作，才考虑后台界面，并说明具体缺口。连接方式不改变本次任务授权范围，凭据不写入主题或 Skill。

## 备份主题的模板预览配合

用户指定：在备份或未发布主题中新增 page、product 或 collection 模板时，线上已发布主题也同步创建同资源类型、同模板后缀名的空模板，使后台可选到该模板，并配合备份主题预览完整效果。例如备份中的 `product.custom-size.json` 对应线上同名模板。

先检查两边模板清单并确认当前线上主题。线上已有同名模板时保留原文件，不覆盖或清空。确需新增时，按目标主题与 Shopify 当前支持的格式创建最小合法空模板；完整 section、配置和业务实现保留在备份主题中。沿用 API 优先、CLI 其次的操作顺序，不为此进入浏览器后台编辑。

创建模板与给具体 page、商品或集合分配模板是不同操作。按用户指定的资源与本次授权处理分配，核对 template suffix 与预览主题 ID。同步空模板本身不等于完成资源分配或完整预览；若现有线上资源被分配到空模板，线上也会使用该模板，因此不能为预览擅自改变现有线上资源的模板绑定。完成后说明两边模板名称、资源绑定及实际预览验证结果。

## 默认开发约定

- 先读取目标主题中功能相近的 section、schema、共享 snippet、样式变量、JS 组件、资源加载及编辑器生命周期。复用当前主题的实现和调用约定；不将 Dawn 的类名、断点和组件直接搬进其他主题。
- 首页区域做成独立 section，在编辑器中添加、删除、排序和配置。其他页面遵循目标主题的模板组合方式。内容差异优先通过参数、settings、blocks 或结构化数据表达，避免复制整份产品页。
- 同类商品卡片在首页、分类页、产品推荐等位置调用同一个主题公共组件。差异通过参数控制。修改公共实现时核对各调用位置；商品详情主体不与卡片强行合并。
- 按钮、输入框、弹窗、折叠、轮播、价格展示优先复用主题已有能力；公共 header/footer 接入既有 layout 或 section group。
- 字体、主题色、颜色方案、宽度、间距与动画引用主题设置和约定，响应全局设置及减少动态效果偏好。确需模块级差异时提供符合主题习惯的配置。
- 用户维护的图片、视频、文字、链接、商品、集合和重复条目均可后台编辑、选择或上传。固定界面文案使用主题翻译机制。空配置有合理表现，不硬编码旧店素材或内容。
- 店铺专属标识、商品映射、插件字段和业务参数与实现逻辑分开，放入适当配置层；无需把每一行 CSS 和程序逻辑暴露为运营选项。
- 保持轻量、易读和可修改。复用个人配方的思路，补齐依赖、实例隔离和主题适配；笔记不是可直接上线的组件。

## HTML 或设计稿还原

用户提供 HTML、设计图或参考稿时，以其为视觉依据，目标为 98% 以上还原。先提取布局层级、间距、字体与字重、字号行高、尺寸、颜色、边框和响应式行为，识别重复 HTML 结构与公共 CSS，再转换为当前主题的 section、block、snippet 和配置。公共结构和样式统一复用，避免每个模块各写一套。

同时遵循主题原生融合约定：优先将设计值映射到主题已有样式、字体设置、颜色方案与组件；设计存在明确差异时，通过符合主题架构的模块配置或有作用域的样式实现，避免直接改动全站公共样式影响其他页面。字体文件和素材缺失时说明对还原的影响，不用替代素材声称已达到精确还原。

图片、视频等用后台媒体选择或上传，文字和链接用可编辑配置；商品内容通过商品选择器引用真实商品，由共享商品组件展示。集合商品区通过集合选择器统一选取集合，并循环读取该集合商品，不把集合内每个商品拆成零散的单独配置或硬编码调用。仅在设计明确要求人工精选且不按集合组织时，使用统一商品列表选择配置。标题、价格、图片、链接等来自所选商品或集合数据，避免重复手工录入。

在与参考稿相同的视口下逐项检查布局、间距、字体、素材、公共组件及移动端效果，并迭代修正。98% 以上是用户要求的验收目标，不是未经测量可宣称的结果；交付说明已核对的视口、剩余差异与缺失条件，不虚构还原百分比。

### 多页面设计稿的 header/footer 统一规则

用户明确要求：一系列 HTML 或设计稿中的 header、footer 不一致时，以首页版本为唯一标准，所有页面统一共用，没有页面例外。其他页面稿中的不同页头、页脚不作为实现依据，也不为了逐页还原而保留差异。此规则优先于逐页设计稿的视觉还原要求。

将首页确定的 header/footer 按目标主题的原生架构实现为唯一公共组件，通过既有 layout、section group 或对应公共机制供所有页面引用。导航、Logo、文案、素材及样式配置共用同一来源，不复制到各页面 section，不建立页面专属替代版本。首页的移动端表现、交互、字体和配色同样统一复用。

若提供的材料无法辨认哪份是首页，先确认首页依据再决定公共版本，不擅自从不同页面拼出另一套。验收核对所有交付页面是否使用同一公共实现，并确认修改公共配置会统一生效。

### Dawn 空元素隐藏兼容

还原 HTML 时必须检查目标主题的 `:empty` 规则。本地审计的 Dawn 15.3.0 在 `assets/base.css` 对 `div:empty`、`section:empty` 等指定标签设置 `display: none`；其他主题和版本以实际源码为准，不能假设所有空标签都会隐藏。

识别设计中有视觉职责的空元素，例如 Banner 背景色层、背景图片层、遮罩、装饰形状和布局占位。它们即使没有文本子节点也可能必须显示；CSS 背景和伪元素并不会让元素摆脱 `:empty` 匹配。将这项检查纳入 HTML 转换和视觉验收，避免背景丢失或布局塌陷。

用户明确指定的默认修复方式：保留设计中有视觉职责的空元素，给它明确的模块专用类，在对应模块内使用 `display: block !important` 覆盖主题的 `display: none`。不要仅为规避空元素隐藏而重构原设计结构。若该元素设计上需要 flex 或 grid，则使用对应的 `display: flex !important` 或 `display: grid !important`，保留必要的响应式显示规则。例如：

```css
.custom-banner .custom-banner__background:empty {
  display: block !important;
}
```

示例类名需替换为当前模块实际类名。确认元素有必要的尺寸、定位及层叠关系；纯装饰元素按需设置 `aria-hidden="true"` 和不拦截点击的行为。

不要全局删除主题的空元素隐藏规则，不要用通配覆盖强制显示全部空元素，也不要插入无意义文字或空格来规避问题。只修复有明确视觉职责的元素；未配置的内容模块仍遵循原有空状态逻辑。验收包括 Banner 背景、遮罩和装饰在桌面、移动端、编辑器重载与空配置下的表现。

## 实施与交付

实现前简述本次复用哪些原生文件或组件、新增哪些模块、运营配置放在哪里。若尚未取得目标主题源码，明确缺少的依据，不声称已完成原生适配。

验证与变更范围相称：配置可编辑、桌面与移动端、同页多实例、编辑器重新加载、全局字体配色与动画继承；公共组件核对跨页调用。涉及交易的变更额外验证价格与购物车链路，细则见计价参考。

每次完成用户的修改需求，最终回复必须包含可点击的预览链接和具体修改位置。预览链接应指向本次实际开发的主题及相关页面；备份主题使用对应主题的预览链接，不能只给线上首页或后台管理地址代替。涉及多个页面时列出对应预览入口。根据实际店铺、主题和页面信息生成并核对链接，不猜测 URL；无法取得有效链接时明确原因及缺少的条件，不声称预览已就绪。

用简明列表说明改了哪个页面、哪个模块或位置，以及具体改动和效果；附相关修改文件、后台配置入口和必要的依赖及实际验证结果。让用户能从链接直接查看，并知道重点检查哪里。

区分源码事实、用户业务规则、官方文档和未验证推断。这份 Skill 提供开发方法，不绑定旧店账号、访问令牌或发布权限。
