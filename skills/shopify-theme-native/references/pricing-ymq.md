# 复杂定制、公式报价与 YMQ

沿用主题原生 UI 和交易组件，将规格状态、规则计价、插件适配的职责分清。可以是轻量模块和函数，不要求额外框架。

## 先确定交易含义

确认输入单位、合法范围、规格方向性、配件限制、计价系数、边界、舍入规则及可核对报价。区分三种策略：固定规格选择原生 variant；公式总价减已收取的基础价得到附加价；插件接收全额价格。不能未经核对混用这些策略。

明确每笔金额由哪个 variant、附加商品或插件机制收取，是否还包含数量、配件、币种转换和折扣。屏幕报价不等于最终收费。

## 实现方式

- 用统一状态表示当前合法规格和配件。规格变化导致选项失效时，同时清除状态、界面选择与对应附加价。
- 将计价写成可独立验证的函数，输入输出含义明确，参数来自业务配置。无效输入不生成可提交报价。对精度与舍入采用明确策略。
- 映射 YMQ 字段、选项标识、金额属性与事件的代码集中在适配层；显示层不散落插件选择器，也不各自复制公式。
- 先核实目标店使用的 YMQ 版本、官方支持接口及实际加载链路。历史 Inyouths 代码通过字段值、`ymq-option-price` 属性及 bubbling change 事件对接；这是已观察到的店铺实现，不证明存在稳定公开 HTTP API，也不保证新站同样适用。
- 若接口依赖 DOM，记录其依赖并验证初始化、延迟加载、重渲染和选项切换。插件未就绪或同步失败时防止提交不完整配置，给出可恢复提示。
- 复用主题价格展示、加购和购物车更新机制；避免重复提交。展示面板读取统一报价结果，不再维护另一套计算。

## 验证重点

用业务确认样本检查正常规格、最小最大规格、阈值两侧、宽高互换、舍入、配件启停与非法输入。历史公式可能非对称或存在分段跳变，不自行把跳变平滑化，也不当成新站的有效定价。

交易验证依次核对：输入状态 → 计算金额 → 插件选项和附加价 → 购物车行项目/数量/属性 → 可观察到的结账金额。不要为测试创建真实订单或扣款，除非用户明确要求。无法验证后续环节时明确范围，不能用 JS 语法通过或公式探针替代交易验证。

旧店商品 ID、SKU、字段名、基础金额和公式系数只是审计证据。新站重新建立映射和报价样本。密钥不写入主题前端或 Skill。
