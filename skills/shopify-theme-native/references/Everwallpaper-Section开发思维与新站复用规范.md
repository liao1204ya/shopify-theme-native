# Everwallpaper：Section 开发思维与新站复用规范

版本：1.3｜分析日期：2026-09-07｜补充：个人基础模块笔记与跨主题原生架构、UI 继承、后台配置要求｜适用范围：Shopify Liquid 主题；Dawn 为案例，不是所有主题的统一代码基线。

## 1. 这次真正提炼出的结论

**页面组合与公共组件原则（用户进一步明确）：** 首页每个内容区域是独立 section，内容与素材通过后台自定义、选择或上传；分类页、产品页等继续按目标主题的模板和模块结构组织。跨页面相同的商品卡片调用同一个主题 snippet／公共组件，通过参数控制显示差异，修改一处统一生效。section 是页面区域，商品卡片是区域内部的共享组件；不因所在页面不同就复制多份实现。以后新站的新增与修改默认采用这一方式。

**跨主题首要约束（用户明确要求）：** 新增 section 或其他公共模块，必须先读取并引用当前主题的架构与写法，包括原生 UI 组件、动画及开关、公共 header／footer、全局字体和主题色。新页面接入主题既有 layout 与页头页脚机制；样式引用主题变量和颜色方案。模块内容与图片、视频等素材通过后台配置、选择或上传，重复条目通过 blocks／数据维护，不将内容、素材地址及店铺业务参数写死。更换主题时保留开发思路，重新适配目标主题，不直接照搬 Dawn 的类名、断点或动画实现。下文历史源码中的硬编码是审阅事实，不是未来开发要求。

按你对蒸馏重点的明确说明，本文件首先保存：**以原主题架构为基础，让每个自定义 section 和原生 section 一样配置、组合、复用；用自己的基础模块配方补充业务需要。**

具体而言，继续使用主题的 sections、snippets、assets、JSON templates、settings 和 blocks，沿用主题的 page-width、配色、字体、标题尺寸、间距及交互习惯。自定义模块能与原生模块放在同一页面中自然协作。这里的架构建议是整理现有职责，不是要求另建一套应用框架或把主题整体重写。

复杂公式与 YMQ 插件协作另见《Inyouths-复杂定制计价与YMQ协作开发方法.md》。下文保留 Everwallpaper 商品定制与维护问题作为案例证据，不将其作为这一站最主要的能力标签。

尺寸、材质、裁剪、上传、样品、安装指导说明这些模块如何服务壁纸业务。最值得带到新站的是沿用 Dawn 基础模块、只对必要环节做定制的判断，以及把自定义模块做成主题内部可复用积木的方式。

结合你补充的基础模块，完整的方法应表述为：**积累参考 → 提炼常用效果 → 套用统一 section 骨架 → 组合交互 → 接入商品数据 → 形成业务页面 → 把可复用部分存回个人库。** 参考库到实现之间的具体过程没有历史记录，属于依据材料作出的归纳；骨架、交互配方和数据访问配方则有直接文件证据。

你已经有模块化复用意识：CSS 小配方、FAQ、Tab、视频、基础 section 和元对象遍历分别被保存下来。前版“复制整页较多”的判断只适用于现有主题中多套商品主体的落地方式，不能概括你的全部开发思维。下一步是把这套个人配方库变成依赖明确、支持多实例、有数据契约的稳定模块库。不必为了抽象而重写所有页面；真正重复、需要同步修改的部分才值得提取。

这里的“你的方式”指交付主题体现出的实现模式。源码快照没有作者、提交历史和工具使用记录，无法判断每段代码是否由你独立编写，也不能据此给个人编程水平打分。下文将代码事实、业务价值推断和改进建议分别说明。

### 一个值得保留的判断：你并没有把所有东西都重写

首页模板包含 10 个 section 实例，主要由 Dawn 的轮播、商品集合、图文、多列模块组成，再加 shop-ins。FAQ 页面也沿用原生 collapsible-content。

这说明有价值的工作同时发生在两层：一层是把原生能力组合成有效页面，另一层是围绕壁纸业务补齐主题本来不具备的能力。新站继续遵循这个顺序：**先配置，再扩展，确有独立职责时才新增模块。**

## 4. 你的思维模式：保留什么，升级什么

### 4.1 先解决客户任务，再决定模块

源码体现出的用户任务链是：找到喜欢的图案 → 确认场景效果 → 选择颜色／材质 → 输入墙面尺寸 → 确认裁剪 → 下单 → 获得测量和安装帮助。样品版又补上“先验证材质和图案”的低门槛路径。

新站应先写这条任务链，再安排 section。一个模块必须说清楚它消除了什么疑问、收集了什么输入、促成了什么下一步。不能只写“做一个漂亮卡片”。

### 4.2 把运营需要改变的内容开放出去

你大量使用 schema settings 和 blocks 来配置标题、图片、说明、链接、步骤。这使内容更新不必每次改 Liquid，是值得继续发展的能力。

升级方向是“有边界的可配置”：重复内容用 blocks，富文本用适合的内容字段，商品关系用结构化数据，链接用资源／链接设置。不要让普通运营人员在 textarea 中维护 HTML 和脚本。像 `tas`、`contant`、`p-a` 这样的字段名也不适合成为新站规范。

### 4.3 你已经开始区分交易对象与附加信息

尺寸购买使用 variant 与 quantity 承接金额，使用 line item properties 携带 Wall Size、Cropped Image Url；样品版以统一样品商品承接交易，再附带来源壁纸信息。这是从页面开发走向业务建模的关键一步。

需要进一步明确：订单属性负责描述定制需求，不能单独作为价格或履约授权依据。后台实际商品、计费单位和履约规则必须与前端模型一致。

### 4.4 快速交付已经成熟，共享边界还需要建立

复制页面能迅速实现业务差异，尤其适合需求还在变化时。问题出现在同一段逻辑需要多处同步修复时。

建议以“共同变化”作为抽取标准：两个页面都需要同一项价格修复、同一套材质说明或同一种上传错误处理，就应考虑共享。纯内容不同优先共用模块；流程真正不同才保留不同控制器。不要把五个大文件简单合成一个更大的条件分支文件。

## 5. 有源码依据的主要问题

这里的优先级表示新站迁移／后续修复顺序，不表示已经测得线上损失。

### 优先处理：购买状态与上传失败

**事实：** `assets/product-cropper.js:350` 附近的购买处理先取得裁剪画布，上传成功后再设置订单属性与数量并提交。失败分支主要写 console，没有完整的用户错误恢复；没有明确的 busy 防重复提交锁。输入无效时也没有统一清空全部购买状态。

**影响：** 上传失败、快速重复点击、先输入有效尺寸再删除尺寸时，需要验证按钮与旧裁剪状态是否一致。不能仅因为存在 cropper 对象就认定当前输入有效。

**新站规则：** 使用明确状态“待输入／无效／预览可用／上传中／加入购物车中／成功／失败”；每次提交重新验证尺寸、可售 variant、当前裁剪和上传结果；失败必须显示提示、恢复按钮、允许重试。画布生成本身也要在错误处理范围内。

**补充事实：** `sections/custom-content.liquid:298` 的独立上传表单，在上传开始和 finally 中均将提交按钮设为 disabled=true，成功分支未恢复。它未被发现直接 JSON 引用，因此列为旧模块中的确定性逻辑问题，不能说当前线上联系表单一定坏了。

### 优先处理：复制的商品主体与混乱的价格状态

`main-product.liquid` 为 2,389 行，repeat 2,310 行、special 2,274 行、sample-special 2,285 行、upload 2,504 行。行数包含大量继承的 schema，不能据此说它们都是新逻辑；但共同主体多份存在，会扩大升级和修复范围。

`product-cropper.js:55` 起把 base_price 的 data-price 从整数金额改成小数字符串，又从其他 DOM 属性读取数量和价格；初始化写 `$`，材质点击分支写 `&#163;`。这是源码中可确认的不一致，不代表所有可见总价一定显示错币种。

新站以整数最小货币单位保存价格，以独立数值保存计费数量，只在展示时格式化。商品展示、材质变化、折扣价和购物车提交应从同一个状态推导，避免读写 DOM 充当业务数据库。

### 优先处理：section 无法独立搬走

`Image-slider.liquid:57` 直接初始化全局 `.mySwiper-video`，而 Swiper 的资源加载出现在 `main-product-upload.liquid:33、61`。当前上传模板将两者放在一起，因此可以碰巧满足依赖；把轮播搬到其他页时，依赖就可能缺失。

它只在 DOMContentLoaded 时初始化，也没有明确的编辑器卸载清理。`product-desc.js` 和 `product-repeat.js` 对整页 tab 和内容分别建立索引，也依赖页面结构一一匹配。

新站要求每个模块声明自己的资源依赖，以自身根节点查询 DOM；添加同一 section 两次、编辑器重新渲染、删除模块时都能正确工作。相关平台事件见 [Shopify 编辑器集成文档](https://shopify.dev/docs/storefronts/themes/best-practices/editor/integrate-sections-and-blocks)。

### 优先处理：全局 CSS 把页面模块绑在一起

`page-Install-heavy.liquid:19` 及 peel 对应文件在移动端直接改 h1、h2、`.page-width p`。`page-custom-wall.liquid` 又覆盖 `.multicolumn`、`.field__input`、`.slider-button` 等其他组件的选择器。

这可能是为整张页面快速统一风格，但无法作为独立 section 的默认行为。新站将局部样式限制在模块根类名内；确属整页风格的规则放在明确的页面容器下，避免通过一个 section 隐式控制其他模块。

### 优先处理：移动端轮播缺少图片回退

`slideshow.liquid:142` 起给桌面图片加 small-hide，只有填写 imagem 才输出移动图；移动端自适应比例也改为读取 imagem。只配桌面图时，手机可能没有可见主图。

移动端专图是正确的运营能力，但必须允许未配置时回退桌面图。可考虑 picture/source 组织响应式资源；不能仅凭 CSS 隐藏就认定另一张图片一定不下载，实际请求还需浏览器验证。

### 明确的资源缺失与兼容风险

- `page-custom-photo.liquid:249` 引用 assets/jquery.min.js，但主题文本和资源清单中没有该文件；静态校验也确认缺失。不能假设应用注入一定补齐依赖。
- `page-Inspiration.liquid:263、306` 加载 jQuery 3.1.1，同时使用 `.load(handler)` 旧事件写法。该写法在 jQuery 3.0 已移除，属于可确认的 API 不兼容；前台是否有额外兼容层未验证。依据：[jQuery 官方说明](https://api.jquery.com/load-shorthand/)。
- `custom-content.liquid` 引用缺失的 icon-success、icon-error snippet，并保留失效翻译键。迁移旧代码必须核对目标 Dawn 版本中的图标、资源和 schema，不能只复制 section 文件。

### 中期整理：可编辑不等于必须开放 HTML

`product-content` 的 block content 使用 liquid 字段，商品模板里嵌入大量 HTML 和问答内容。这种方式灵活，但内容、样式和交互结构一起存进配置，运营改文字可能破坏结构。

建议把常规问答收敛为“问题＋答案” block，材质说明变为结构化条目；仅给确实需要定制代码的少数位置保留高级扩展。Tab／折叠头目前是可点击 h3，应改为有键盘行为、状态表达的控件。普通 FAQ 可以继续复用 Dawn 的 collapsible-content。

### 中期整理：硬编码降低新站复用能力

`main-collection-footer.liquid:2` 起直接列出房间和颜色 handle，并用字符串匹配决定入口显示，后续还移除固定旧站域名来提取集合。`custom-size.liquid` 也按 variant.title 的英文关键词匹配材质图，并使用固定 CDN 图片。

这是业务分类意识的体现，但分类应迁移到菜单和结构化关系中；材质应有稳定内部标识。显示名称可以翻译或调整，不能因此改变业务判断。不要直接把旧站域名、邮箱、商品 handle、SKU、CDN 图片和追踪配置复制进新站。

### 静态验证结果应该怎样理解

本次对五个代表性线上文件运行 Shopify 校验：Image-slider、product-content、slideshow 在该校验器中通过；page-custom-photo 与 custom-content 未通过，详情见 audit/validation-live.txt。校验器使用了本地回退 schema。

样品版新增的两个 snippet 均通过本次静态校验，见 audit/validation-sample.txt；校验时远程文档更新请求连接重置，工具使用缓存文档和本地回退 schema 完成检查。此结果不包含商品库存、购物车交互或履约验收。

## 7. 新站应采用的思维架构

### 7.1 六个职责层

|层|负责什么|不应承担什么|
|---|---|---|
|主题基础层|Dawn 的布局、全局设计设置、基础商品和购物车能力|某个旧站的尺寸规则、固定活动逻辑|
|页面组合层|JSON templates 与 section groups 决定模块顺序、配置及不同页面组合|大量内嵌交互代码|
|内容数据层|商品、variant、内容关系、材质说明、指南和菜单|通过英文标题或 URL 子串猜业务类型|
|Section 层|一个用户任务的界面与运营配置，组织自身 blocks|修改整页所有同名按钮、输入框或标题|
|共享能力层|尺寸计算、材质选择、预览、样品、上传、FAQ 等可复用逻辑|反向依赖某个页面上“恰好存在”的 DOM|
|外部服务与履约层|图片存储、原稿关联、订单属性解释、计费和履约校验|把生产可信度完全交给浏览器输入|

核心原则：页面选择能力，配置提供差异，数据描述业务，组件隔离状态，服务负责边界。

### 7.2 新模块从七个问题开始

1. 客户要完成什么任务，最容易在哪一步犹豫？
2. 哪些内容是运营经常修改的，哪些规则应固定？
3. Dawn 是否已提供大部分能力？
4. 新模块的输入、输出、空值和失败状态是什么？
5. 同一模块在一页出现两次，是否仍然正确？
6. 搬到另一家店，需要替换哪些数据和外部服务？
7. 怎样证明它工作正常，而不只是截图好看？

### 7.3 选择复用方式

|遇到的差异|优先方式|
|---|---|
|同一结构，只有文字和图片不同|同一个 section，通过 settings／blocks 配置|
|同一任务，不同商品数据|共享模块＋产品级结构化数据|
|同一页面能力，不同排列顺序|不同 JSON template|
|重复的局部展示|参数明确的 snippet|
|重复的计算、上传或状态转换|独立 JS 能力，共享实现|
|独立任务且运营需要拖放|新增 section|
|短期活动且确实一次性|允许专用模板／模块，但记录依赖与下线条件|

### 7.4 为未来的开发者保留这些硬规则

- 新模块使用项目统一前缀，例如 ew-，文件名统一小写 kebab-case；不要出现 Image-slider／page-Inspiration 这种混合命名。
- section 根节点和交互控件 ID 带实例标识；JS 查询限制在根节点内。全局 dialog 必须明确只能有一个，以及如何接收当前来源商品。
- blocks 正确输出 shopify_attributes；支持编辑器添加、重载、排序和删除时的初始化与清理。
- 初始化可重复调用而不重复绑定事件；卸载销毁实例、监听器和进行中的任务。
- 资源随能力声明，按需要加载；迁移资源和依赖时记录来源、版本和许可，不盲目复制旧库。
- 内容采用合适字段类型；普通运营不必编写 HTML。面向买家的固定 UI 文案使用翻译键。
- 图片提供合适尺寸、宽高和缺图状态；首屏与非首屏资源区别处理。性能收益以实际测量为准。
- 交互使用按钮、输入控件、details 或 dialog 等语义结构；键盘、焦点和错误状态一起设计。
- 新站不要继续通过全局 CSS、固定 ID、英文标题匹配或固定等待时间连接模块。
- 主题文件和最终规范不保存管理 API 凭据。只将店铺必要的公开配置交给前端。

## 8. 定制交易能力的数据契约

### 尺寸与价格

当前代码按平方英尺向上取整作为 quantity：英寸为宽×高÷144，厘米为宽×高÷929.0304 的近似实现。新站必须先确认“向上取整到一平方英尺”是业务规则，不能因旧代码如此就默认沿用。

|数据|约定|
|---|---|
|尺寸输入|保存原始宽高和单位；验证有限数、正数及业务上限|
|标准面积|在一个共享计算函数中换算，避免多个 UI 重复公式|
|计费数量|明确取整规则、最低收费和允许的增量|
|材质|稳定标识＋对应可售 variant；名称和图片属于展示数据|
|金额|使用商品真实价格与计费数量推导，整数金额计算，最后格式化|
|裁剪|关联当前图片与尺寸；输入改变后旧裁剪不能继续当作有效结果|
|订单属性|保存客户选择与履约需要的数据，并定义字段版本|
|校验责任|浏览器负责反馈；可信服务／履约流程核对规则，不依赖隐藏按钮防止改数量|

旧实现上传的是约 500×500 配置下的裁剪预览。这足以服务预览的可能性，不代表能作为印刷原稿。新站要另行确认原始高清图、裁剪位置、镜像状态和订单之间如何关联；本次没有读取外部上传服务或工厂系统。

### 上传接口

明确允许格式、大小、错误格式、超时、重试、上传结果字段及文件访问方式；成功以服务返回完成为准，不能用等待 500ms 当作完成信号。预览生成、原稿上传和加购应分别有可见状态。

### 样品

明确样品商品、材质映射、组合包 variant、适用品类、尺寸说明和来源壁纸字段；价格从真实 variant 读取。素材使用配置／商品数据，避免带着旧店 CDN 地址跨站。固定设计组合包与当前壁纸样品不得混淆。

## 9. 一个可执行的新站迁移顺序

1. **建立干净基线。** 固定目标 Dawn 版本，保存原生快照和版本信息。
2. **绘制任务链。** 确认新站是否真的需要尺寸、裁剪、上传、样品、安装说明；按业务选择能力。
3. **先配置原生模块。** 完成首页、FAQ、基础内容页；验证普通商品与购物车路径。
4. **迁移低耦合内容模块。** 场景图库、案例、步骤指南；先移除全局 CSS 和隐藏依赖。
5. **建立共享商品能力。** 拆出尺寸与金额计算、材质选择、裁剪和上传，逐个接入商品模板。
6. **接入样品。** 创建或映射实际商品数据，统一价格与样品文案，限定适用范围。
7. **盘点站点依赖。** 替换旧域名、邮箱、SKU、图片、外部服务、菜单关系、追踪和应用引用。
8. **按下面的验收表完成验证。** 保存预览、结果和可回退版本，再按该项目授权流程发布。

不建议先把旧主题全部拷到新站再到处替换品牌名。原样保留代码最省初次搬运时间，却会把不再需要的业务假设一起带过去。

## 10. 新站验收标准

|场景|应满足的结果|
|---|---|
|内容为空／图片缺失|不出现破图、无意义空链接或 JS 错误；移动图回退正确|
|同页放两个相同模块|点击、输入、轮播、样式互不干扰|
|编辑器添加、修改、删除、再添加|无需刷新恢复交互，无重复监听和遗留遮罩|
|尺寸计算|12×12 英寸与 30.48×30.48 厘米都对应 1 平方英尺；13×12 英寸按当前取整规则对应 2；同时测试临界值|
|无效输入|空值、0、负数、超限值、单位切换、删改已有效尺寸，均不允许提交旧状态|
|材质与价格|切换可售／缺货材质后，展示、提交 variant、价格与数量一致|
|上传失败与重复操作|超时／错误可见且可恢复；连续点击不重复上传加购；没有可用图时阻止提交|
|购物车与履约|尺寸、图像引用、材质及计费数量准确；普通商品和样品不被定制商品规则误伤|
|样品|单选、多选、组合包、缺 SKU、缺货、接口失败，以及不同商品模板的说明均一致|
|移动与键盘|窄屏无关键内容溢出；键盘能完成选择、展开、关闭；焦点返回合理|
|语言与币种|切换语言／币种后，价格符号、说明、路由与实际结算口径一致|
|性能|在真实页面检查首屏图片与脚本请求；不以新增多少模块推算性能分数|

|元对象使用.txt|积累从简单字段到关系数据的读取方式|图片列表、单个内容对象、对象列表、关联产品条目分别处理|需先知道真实字段类型；不同用法不是对同一字段可任意替换的语法|
|元对象循环嵌套.txt|以产品关联的分组描述一组相关商品|商品 → 分组对象 → 产品列表，前端由数据生成|标题与产品靠相同下标匹配，需维护顺序；轮播 class 不代表完整轮播实现已提供|
|满意网站.txt|保留跨站参考对象，形成自己的参考资料库|未来可以按模块记录喜欢的细节，再提炼共同规则|目前只是 9 条网址记录，不能据此判断具体审美偏好、作者归属或这些网站当前实现|

### 13.2 这套库揭示了六个稳定倾向

**一、你用“场景问题”记忆代码。** 文件名是“两行”“下划线”“移动滑动”“30 天新品”，说明你的索引方式接近实际工作中遇到的问题。新站可以保留这种易查找的命名，再补上技术名称和适用范围；不必把它改成只有开发者能读懂的分类。

**二、你已经有固定的 section 外壳。** padding_top／padding_bottom、750px 断点、移动端 0.75 倍间距、page-width、颜色方案和标题尺寸反复出现。它们多数沿用 Dawn；你的方法价值在于选择并固定它们作为起手式，而不是这些语法本身的原创性。

**三、你倾向先用简单浏览器能力解决问题。** 移动滑动用 CSS，Tab 用 active 状态与事件委托，视频用点击替换。结合主题里的 Cropper／Swiper，可以归纳为：小需求保持轻量，复杂需求借助专用库。不能把它概括成一律不用库，也没有必要为了“工程化”强行加框架。

**四、你把移动端当作另一种使用方式。** 不只缩小字号，还考虑滑动列表、选中 Tab 居中、视频比例，以及商品说明的折叠浏览。这种从操作方式出发的响应式思维值得保留。

**五、你已在把运营规则和内容移出页面代码。** 新品标签开放规则参数；元字段和元对象把内容、产品分组从写死的 HTML 中分离。这意味着新站的结构化数据层可以沿着你已有经验发展，不需要另起一套陌生方法。

**六、你的模块库仍是一套工作笔记。** 有短片段、完整 section、辅助 JS、参考网址，也有未完成的拼接。它首先用于帮助你快速回忆和组装，尚不能等同于经过统一验证的组件产品。下一步应整理每份材料的使用契约，而不是否定这种积累方式。

### 13.3 应保留思路、补齐实现的具体位置

|材料|可直接从文件确认的情况|整理规则|
|---|---|---|
|基础 section、FAQ、Tab|没有 presets；FAQ／Tab 使用了 color_scheme，但各自 schema 没有定义它|若要从编辑器“添加 section”入口使用，补 presets；设置引用与定义成对检查。缺 presets 不等于不能通过模板引用。[官方 schema 说明](https://shopify.dev/docs/storefronts/themes/architecture/sections/section-schema)|
|基础 section|说明文字与标题共同放在 heading 非空条件中|明确“只有说明、没有标题”是否应显示，避免骨架隐含内容依赖|
|FAQ|JS 对整页所有问答统一开合，展开时按当时 scrollHeight 设高度|限制实例范围；图片加载或内容改变后处理高度；使用可键盘操作的开合控件|
|Tab|script 内含未注释的中文说明；初始化只选择第一个 .tab-container|先把笔记说明移出代码；遍历实例、处理空 blocks、使用稳定的面板关系|
|YOUtub|仅解析查询参数 v；JS 放在 endschema 后且没有 script 包装，section 又引用 youtub.js|把末尾 JS 视作另存资源的拼装材料；明确支持的链接形式与无效输入回退，不能把整份 txt 改后缀就安装|
|YOUtub|点击时创建带 controls=0 的 iframe，触发链接没有预置文字|播放后要有可用控制；触发入口需要可访问名称。延后创建 iframe 可减少初始播放器加载，但本次没有测量提速幅度|
|New In|new_badge 在片段内一直为 false；serial 没有定义；标签文案写死|明确是否需要手动覆盖、序号来自当前列表还是全局排名，以及翻译与时间边界|
|元对象使用|最后一段 if 没有 endif；description_2 同时出现在单对象与循环示例中|将其拆为不同数据类型的配方，先确认定义，再录入数据，最后按类型读取|
|嵌套关联|标题数组按商品下标配对，并用 URL contains 隐藏当前产品|优先让每个关联条目同时保存商品和标签；当前商品以稳定身份比较，少依赖 URL 子串|

元字段的 value 返回什么取决于字段类型；单个引用与引用列表必须区分。本次只读了示例，没有读取这些笔记对应店铺的实际定义。依据：[Liquid metafield 文档](https://shopify.dev/docs/api/liquid/objects/metafield)。

### 13.4 把个人库整理成四层，不改变你的工作习惯

|层级|已有材料|整理后的职责|
|---|---|---|
|视觉配方|两行截断、下划线、过渡、视频比例、横向滚动|解决一个局部展示问题，写明适用元素和参数|
|模块外壳|section 基本模块|统一主题语言、间距、宽度、配色、标题和编辑器入口|
|交互配方|FAQ、Tab、YouTube|在独立模块内管理状态、事件、空值与键盘行为|
|数据配方|New In、元字段、元对象、关联分组|定义业务输入及来源，将内容和规则交给展示层|

成品页面则是这些层与具体商品任务的组合。参考网址另存为参考索引，记录你实际认可的模块、观察时间和可借鉴原则；在没有页面证据前，不替你编造喜欢的原因。

每个配方以后只需补一张简短说明卡：**解决的问题、输入参数、数据类型、依赖文件、放置位置、多实例行为、空值与失败状态、验证记录。** 文件有改动时标版本；同一份代码出现在综合笔记和独立文件中时，确定唯一维护版本，其他位置只引用它。

### 13.5 更新后的个人开发原则

> 我习惯把做过的常见效果和交互存成基础配方，用统一的 Dawn section 骨架快速组装页面，再通过 settings、blocks、元字段和元对象适配业务。我重视移动端操作、运营可编辑性，以及用尽量简单的实现完成客户任务。
>
> 未来继续保留这种方式，但将笔记与正式模块区分开：视觉配方保持短小，模块声明依赖，数据先定义类型，交互隔离实例。重复出现的能力回收到库里；每个新站替换业务数据和配置，而不是重复修改多份相同逻辑。

这段是依据主题与个人材料共同归纳的工作准则，可与第 11 节一起交给未来协作的 AI 或开发者。
