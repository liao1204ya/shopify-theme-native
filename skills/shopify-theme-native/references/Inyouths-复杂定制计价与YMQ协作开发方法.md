# Inyouths：复杂定制计价与 YMQ 协作开发方法

版本 1.1｜2026-09-07｜依据线上主题 Inyouths 2026/8/20（151992008873），主题信息 Focal 10.0.0；补充跨主题原生架构与后台配置要求。

## 1. 这次要保存的能力

**页面组合与公共组件原则（用户进一步明确）：** 页面区域通过独立、后台可配置的 section 组合，素材可选择或上传；首页、分类页、产品页推荐区域等同类商品卡片调用目标主题同一公共组件，差异通过参数表达。复杂定制功能也遵循这一方式，复用已有展示及交易组件，仅扩展所需业务规则，不为每个页面复制一套公共实现。

**跨主题首要约束（用户明确要求）：** 即使是复杂计价与 YMQ 定制界面，也必须遵循当前主题的 section／公共组件写法，引用原生 UI、动画、全局字体和主题色，并通过原有 layout 使用公共 header／footer。模块文字、媒体、商品关系和店铺业务参数通过适当的后台配置、选择或上传管理，不写死。公式与插件协作属于业务能力扩展，不应造成视觉与公共架构脱离原主题。Focal 为本次案例，迁移到其他主题时重新读取其实现约定。

**遇到复杂定制商品，先把规格、公式、配件限制和购买流程建模；自己实现适合客户操作的界面，通过插件接口把业务结果交给 YMQ，再与 Shopify 的商品和购物车衔接。**

这套能力与 Everwallpaper 的重点不同。Everwallpaper 主要保存“顺着原主题架构制作 section”：沿用主题的布局、配置、配色、间距、blocks 和交互习惯，让自定义 section 像原生模块一样组合、复用。Inyouths 主要保存“复杂规则与插件协作”：模块外观只是入口，核心是客户配置、计价结果、插件字段、实际交易之间的一致性。

你的方法不是一遇到复杂需求就重写整套电商系统。源码体现的是：主题负责呈现，自定义逻辑负责商品规则，YMQ 承接选项和价格扩展，Shopify 提供交易对象。值得延续的是这种职责划分，而不是某组旧店的系数或选择器。

## 2. 证据范围与 API 的准确含义

本次只读下载线上主题的 294 个文件条目，其中 292 个为文本，保存在 `audit/inyouths-live/`，清单为 `audit/inyouths-live-manifest.json`。没有改动主题、插件配置或商品，没有执行加购、支付、报价创建等操作。未取得原生 Focal 同版本源码，因此不声称完成 Focal 逐文件差异比较。

在你的业务脚本中，可确认的核心接口是 **DOM 字段与事件协议**：找到 YMQ 对应 input，写入选项值，设置 ymq-option-price，再派发冒泡的原生 change 事件。它属于前端集成接口，不应误写成“已确认调用某个 YMQ HTTP 计价端点”。

YMQ 官方资料介绍多种附加价承接方式，包括草稿订单和绑定 variant；这只能证明插件存在多种实现，不足以判定此店当前使用哪一种。[YMQ 附加价原理说明](https://ymq-app.gitbook.io/ymq-product-options-app/faq/implementation-principle-of-app-option-price-add-on)

本次没有读取 YMQ 管理端选项配置、私有接口文档或真实网络加购链路。下文涉及插件端契约与最终收款的内容，明确作为后续开发必须核验的事项，而不是已验证事实。

## 3. 实际业务链路

### 3.1 镜子和镜柜：自定义控件驱动插件字段

1. 主题根据商品标签选择规则脚本。
2. 客户选择尺寸、配件、灯光、边框和交期。
3. 自定义脚本计算尺寸附加价，并重新判断哪些选项可选。
4. 不再适用的选项，同时清空展示值、YMQ 值和附加价。
5. 对每个变化的插件字段派发 change。
6. 原有主题／插件购买链路处理后续加购；购买面板镜像价格和提示。

`snippets/custom-options.liquid:56–67` 的实际加载分支：

|条件|加载规则|
|---|---|
|rectangle-backlight／rectangle-frame／Fixed-size，且非镜柜|product-rectangle-bsn.js|
|上述矩形分支＋Medicine Cabinet|product-rectangle-medicine.js|
|镜柜再加 recessed-no-bluetooth-speaker|product-rectangle-medicine-no.js|
|round-backlight／round-frame|product-round-bsn.js|

这是“同一类能力，不同产品规则”的雏形。名称中的 bsn 不应被猜测成某个未确认业务含义。目录里的 product-rectangle.js、product-round.js、product-shower.js 也含有相关逻辑，但没有发现它们的直接 Liquid 资源引用；分析当前使用方式应优先依据上表与 section 内实际脚本，不能把所有存在的文件都当作正在运行。

### 3.2 普通淋浴房商品页：数据决定公式

`main-product.liquid:741` 的 U-Shaped 分支与 `:830` 的 Shower Door 分支，读取 `product.metafields.custom.shower_room.value`，使用对应尺寸与单价计价，再将超过商品基础价格的部分交给 YMQ。

这比每种商品手写一套尺寸页面更有复用潜力：商品数据决定需要哪些输入，公式分支决定怎样计算，插件字段承接结果。

### 3.3 定制淋浴房向导：把模型选择变成交易配置

`sections/main-product-custom.liquid` 的实现更加完整：

- section blocks 选择不同参考商品。
- Liquid 生成 productMetaMap，包含商品价、参考 SKU、代理 variant ID、尺寸图、尺寸范围、角度范围、unit_price、zz。
- 第三步按元对象中存在的范围动态创建尺寸输入。
- 第四步按所选商品的 frame_color 数据生成五金颜色。
- 后续汇总尺寸、开门方向、五金、把手等选择，并同步 YMQ。
- 通过参考商品 SKU 与当前配置商品 variant.title 对应，选出实际提交的代理 variant；提交前再次同步表单的 input[name=id]。

这里的 selectVariantBySku 并非直接查询 Shopify SKU API；它在现有 option1 控件及标签中匹配文本。代理 variant 映射则在 Liquid 中通过标题与参考 SKU 相等来建立。保留“参考商品与交易载体对应”的设计，但必须把这个对应关系写成显式契约。

## 4. 三类计价策略：不要混成一个万能公式

### 4.1 离散规格价：圆镜

`product-round-bsn.js` 通过直径选择触发对应原生规格控件，例如 block-swatch-20Inch。尺寸主体价格走原生 variant，配件附加价走 YMQ。

适合：尺寸是有限集合，商品后台可以维护其价格。可复用原则是“原生规格能准确表达的价格继续使用原生规格”，不必为了统一而改为公式。

### 4.2 分段模型价：矩形镜与镜柜

令 x 为宽、y 为高，当前脚本从英寸显示值读取整数；s=x×y，c=x+y+min(x,y)。

成本函数 C 使用如下系数，字段顺序为常数、x、y、s、c：

|区域|常数|x 系数|y 系数|s 系数|c 系数|
|---|---:|---:|---:|---:|---:|
|s < 1900|-61.43767931|2.205711465|1.986026393|-0.000816521|1.415596439|
|s ≥ 1900|299.883986|-2.538633704|-5.360809299|0.123439401|3.117467307|

另一个多项式 M₁ 使用：6.856568154、0.030422952、0.042881326、0.000690259、−0.067146046，字段顺序相同。M₃=(x+30)/(y+30)+2。

估算主体价 P=floor(C×max(M₁,M₃))。

|商品规则|写入 YMQ 的尺寸附加价|
|---|---|
|矩形镜|x+y=40 时为 0；其余为 P−436|
|矩形镜柜|x+y=52 时为 0；其余为 P−628|

这些是源码事实。系数看起来像成本／倍率模型，但没有原始报价表或拟合过程，不能声称它们由何种算法训练、是否反映最新工厂成本。436、628 是脚本中的抵扣常数，不能未经商品数据核对就认定它们永远等于当前 variant 基础价。

公式的重要性质：**宽高有方向性，面积有分段边界，基础规格有特殊规则，取整发生在抵扣前。** 任何“简化”若改变这些顺序都可能改变结果。

本次从源码提取系数并独立复算得到以下数学样本，未确认每个组合均为实际可售规格；金额为公式数值，不是最终结算报价：

|宽×高|面积|P|矩形镜尺寸附加价|
|---|---:|---:|---:|
|20×20|400|489|0（特殊规则）|
|22×30|660|648|212|
|30×22|660|641|205|
|40×32|1280|791|355|
|38×48|1824|876|440|
|38×50|1900|1692|1256|
|50×38|1900|1895|1459|

38×48 到 38×50 的模型输出显著变化，应作为分段规则验收重点；可能有真实生产阈值，不能仅凭变化大就认定是错误。22×30 与 30×22 不同，说明不能擅自排序宽高。新站必须用业务认可的报价样本确认，而不是只验证程序算出一个数。

### 4.3 几何展开价：淋浴房

普通商品页中：

- U 型：P=(L+W1+W2)×H×unit_price。
- 其他支持的门型：P=(存在的 L＋存在的 W＋配置偏移 zz)×H×unit_price。
- 写给尺寸字段的是 max(P−基础商品价,0)。

基础价来自 custom-options-shower.liquid 的 prices 属性；原实现有整数读取，未来如果基础价含小数，要明确是否保留精度。

向导中则根据 W1／W2 是否存在切换几何分支，计算得到的 P **直接写入 title-leo 的附加价**；尺寸字段以零附加价传值，把手尺寸价格单独写入 handle-style-size。向导本地展示为 currentCustomBasePrice＋currentCustomAddonPrice。

因此，普通商品页采用“总价减基础价”，向导采用“把主体计算价写入插件选项”的不同口径。必须核对向导交易载体的基础价、插件的价格模式及实际结算，否则不能排除基础价重复计入。不要让所有品类共用同一个“减基础价”函数而不区分策略。

## 5. 真正值得保留的是约束联动

以当前矩形分支为例：

|尺寸变化|规则表现|应保存的思维|
|---|---|---|
|宽不足 22 或高不足 30|时钟选项失效并清除插件值和价格|几何条件决定配件可用性|
|宽不足 40 或高不足 32|部分电子配件失效并归零|取消配件不能只隐藏界面|
|化妆镜：宽不足 32／32–48／大于 48|禁用，或切换不同配件规格及 35／45 附加价|尺寸变化可能替换配件，而不仅是开关|
|宽或高达到 80|尺寸更新分支限制加急交付|交付能力也是商品规则|
|宽达到 90|边缘工艺失效并清除价格|生产限制应参与配置计算|

圆镜有自己的阈值，例如较小直径限制配件，超过 48 的直径限制加急。不能直接套用矩形阈值。

这套思维应提炼为：**上游选择变化 → 重新计算可选集合 → 清理或替换无效下游选择 → 重算价格 → 同步插件 → 更新购买状态。**

当前实现的具体风险是规则散布在事件中。例如矩形尺寸更新检查宽或高达到 80，而交期选项点击处理只检查宽达到 80；不同入口必须使用同一规则，避免客户按不同操作顺序得到不同结果。此为源码中的条件差异，实际前台影响仍需验证。

## 6. YMQ 适配层应该保存什么

### 6.1 当前字段契约

|业务数据|当前插件字段选择器|当前写法|
|---|---|---|
|镜子尺寸|.ymq_size_money input|尺寸描述＋模型附加价|
|普通淋浴房尺寸|.dimensions input|尺寸描述＋超过基础价的部分|
|向导主体|.title-leo input|所选商品标题＋计算主体价|
|向导尺寸与角度|.length-leo、.height-leo、.width-leo、.wa-leo、.wb-leo、.left-return-angle、.right-return-angle 下的 input|分别写值，附加价为零|
|镜子配件|.makeup-mirror、.demister、.bluetooth-speaker、.clock-wifi 等下的 input|选择文本＋对应配件附加价|
|向导把手|.handle-style、.handle-style-size 下的 input|款式及规格，规格承接附加价|
|交付|镜子 .delivery；旧 shower 脚本 .delivery-time|按具体产品链路写交付值与附加价，不能混用|

这是旧店适配映射，不是全局 YMQ 标准字段名。新店应先建立选项集，确认其生成字段和可用接口，再配置映射。YMQ 官方支持把选项模板分配给多个商品或集合，但不意味着复制 Liquid 就会复制插件配置。[YMQ 选项模板说明](https://ymq-app.gitbook.io/ymq-product-options-app/getting-started/option-template-set)

### 6.2 对接时必须确认的接口合同

1. 插件何时就绪？是否有公开 ready、选项更新或价格更新事件？没有确认过的事件名称不能凭空发明。
2. 如何定位当前商品实例的字段？DOM 选择器、字段 ID 和公开 JS API 各自是否有版本保证？
3. 价格单位是主货币单位还是最小货币单位？是否包含 quantity、折扣、税和汇率处理？
4. 一次更新多项选项是否支持批量提交，是否会中途触发多次重算？
5. 怎样确认插件已接收新值、价格已经计算完成？只发出 change 不等于得到完成确认。
6. 修改选项、移除选项、恢复默认值分别怎样调用？零附加价与空值不是同一业务含义。
7. 加购和结算由谁提交，价格通过什么模式落入交易？哪些主题购买入口需要禁用或适配？

将这些细节集中在一个 YMQ adapter 中。业务规则只表达“尺寸选项为某值，附加价为某数”，不要在几十个分支里复制插件选择器和派发事件的代码。

本次没有获取到明确说明 ymq-option-price 的公开版本化 API 文档，因此将其标记为“当前源码可见的对接约定，迁移时需验证”，而不是永远有效的官方承诺。

## 7. 从现有方式升级出的可复用架构

|职责|输入／输出|已有证据与下一步|
|---|---|---|
|主题 section|呈现控件和配置入口|继续沿用目标主题的基础架构，不为计价另造一套网站架构|
|产品规则配置|产品模式、尺寸范围、系数版本、选项价格、插件映射|已有 tags 和 shower_room 元对象；将隐含文本规则改成稳定标识|
|配置状态|当前型号、variant、尺寸、方向、配件、交期|当前部分来自 DOM；逐步改为单一状态对象|
|约束计算|状态 → 可选项、无效项、修正后的状态、缺失项|已有取消配件时清价的意识；集中实现，避免入口不同规则不同|
|价格计算|有效状态＋规则版本 → 主体价、各附加项、总额及计算依据|保留离散 variant、分段模型、几何公式三种策略|
|插件适配|业务值与附加价 → YMQ 字段／经确认的 API|集中定位、就绪、写值、清值、更新和错误处理|
|展示同步|插件确认价／统一报价 → 主价格、汇总、辅助面板|iyra-purchase-panel 已通过观察现有节点同步，值得保留“展示不重算另一套价格”的方向|
|交易核对|variant＋配置＋插件价 → 购物车／结算一致性|提交前重新校验；不能把隐藏按钮当作唯一校验|

建议的状态流程是：初始化 → 等待插件就绪 → 接收输入 → 校验与约束归一 → 计算报价 → 同步插件 → 确认同步 → 允许提交。期间出现缺字段、无效数值或映射失败，进入明确错误状态，不沿用旧价继续购买。

这是对现有方法的整理目标，不代表这些边界已经全部在旧代码中实现。

## 8. 新项目的固定开发步骤

### 第一步：先拿到规则，不急着写公式

记录每种产品的输入、单位、最小最大值、步长、配件限制、交期限制、默认规格、基础价、报价样本和舍入要求。生产提供的是总价、成本还是倍率，必须分清。无法确认的部分明确留空，不用代码猜。

### 第二步：先定义数据，再填值，再读取

为每种产品规则确定字段类型和关系，录入真实样例，再让 Liquid 读取并生成前端配置。元对象里的 unit_price、zz、范围和代理商品关系应有明确含义。新增产品能够通过配置接入的内容，不应再复制整段 JS。

### 第三步：选择计价策略并固定计算口径

有限规格使用 variant；连续尺寸使用经验证的模型；展开面积使用几何公式。明确是否抵扣基础价、取整位置、数量乘法位置、货币单位和最低价政策。不能默认为所有负附加价都合法，也不能未经业务许可统一截为零。

### 第四步：先做最小插件闭环

在测试商品／预览环境验证一个字段：写值、写附加价、触发更新、确认主价格、加购、查看结算金额。确认插件模式与支持接口后，再扩展复杂 UI。真实购买测试应按项目授权执行，不能通过生产下单来猜接口。

### 第五步：加入依赖规则与操作顺序测试

重点验证“先选配件再缩小尺寸”“先选加急再改成超大尺寸”“从一种门型切换到另一种”。每次变化都需同步可用性、选择值、价格、概要和插件字段。

### 第六步：最后连接完整界面

沿用主题 section 外壳和原生表单，补足多实例、编辑器重载、键盘操作、错误提示和慢网络状态。展示增强不能悄悄接管另一套价格或提交逻辑。

## 9. 把经验变成验收，而非只保存代码

|测试组|具体样例或条件|需要核对|
|---|---|---|
|公式正确性|业务认可的基础规格、中间尺寸、最大尺寸报价表|计算值与业务期望一致，而非仅与旧程序一致|
|分段边界|面积小于、等于、大于 1900|是否预期跳价，取整次序是否正确|
|宽高方向|22×30 与 30×22 等交换样例|产品规则是否允许非对称价格|
|默认特殊规则|x+y=40／52；同和不同尺寸|是否应按和判断，还是需要准确的宽高组合|
|无效数据|空值、非有限数、负数、超限、小数尺寸|阻止旧状态或 NaN 写进插件|
|配件联动|跨越宽 32／48、电子配件阈值、加急尺寸阈值|界面、插件值、附加费同步取消或替换|
|型号切换|参考 SKU 缺失／重复，代理 variant 不存在|明确阻止提交；不静默使用前一个 variant|
|插件同步|晚加载、字段不存在、重复事件、快速连续修改|只能提交最后一次有效配置|
|交易一致性|数量 1／2，改变基础价，带附加项和不带附加项|主价、附加价、总额和实际购物车／结算一致|
|多币种与格式|本地化金额及小数基础价|避免把格式化文本错误转成数字|
|向导路径|前进、后退、跳过第二步、切换门型／把手|隐藏步骤不残留旧选择或附加费|

当前值得优先完善的技术点：

- 多处采用 setTimeout(500) 等待默认字段同步，不能保证插件已就绪。
- 镜子模型抵扣固定常数，淋浴房读取基础价，两者不能混用；向导写完整主体价更要核对交易载体。
- 配件价从展示字符串剥离，规则依赖英文名称与 150／170 文本替换；应改用独立业务 ID 和数值。
- 旧 shower 输入校验只比较大小，NaN 不能通过这种比较可靠识别；向导已显式检查 isNaN，体现了不同阶段的实现差异。
- 向导注释仍称“仅编辑后计算”，但实际初始化会调用 recalcIfEdited，edited 不再控制主计算分支。审查应以可执行路径为准。
- 向导查找代理 variant 失败会返回 false，而提交同步监听没有据此阻止提交；应验证缺映射时的行为。
- 购买面板若从价格文本回退解析，会移除逗号；对逗号作小数分隔的格式需另行验证。最好使用单位明确的数值接口。

这些是复用时的完善事项，不是本次已修复或已确认造成订单损失的问题。

## 10. 以后交给 AI／开发者的工作说明

> 遇到复杂定制商品，采用我的 Inyouths 方法：自建适合客户的配置界面，先明确产品数据、约束和计价策略，再通过经过确认的 YMQ 接口同步选项与附加价，保留主题及插件原有交易职责。
>
> 自建界面仍沿用目标主题的架构、公共组件、UI 动画、字体和主题色，页面共用原生 header／footer。模块内容与素材通过后台编辑、选择或上传，业务参数进入配置层，不写死旧店数据。
>
> 先选择离散 variant 价、分段模型价或几何公式价；写清单位、基础价抵扣、舍入、数量和货币口径。尺寸变化后同时更新配件可用性、已选值、附加价和购买状态。公式应与 UI 分离，插件映射集中在适配层。
>
> 不直接复用旧店固定系数、436／628、SKU 映射和 DOM 选择器。把它们视为配置及版本化契约。没有插件文档或运行证据时，不编造 API 名称、事件或结算模式。
>
> 在业务认可的报价样本、规则边界、插件同步和购物车／结算一致性验证通过后，才把模块视为可用。截图正确和 JS 语法通过不等于计价正确。
